# fork-updates-r10m — адаптеры Telegram, Twitter и Twilio Phone

## 1. Шапка

- Репозиторий `chaskiq`, ветка `main`, 2026-11-22. Исполнитель Qwen Code (`qw2`).
- BASE_SHA: `1578624b1a0ae6618df1154167427e4a2f717530` — Record R10 programme status.
- Очередь и границы определяет [программа R10](fork-updates-r10-programme.md).
- Цель — убрать семь нарушений RuboCop в трёх адаптерах, сохранив запросы,
  записи базы, порядок побочных эффектов и публичные методы.

## 2. Где работать

Открой одноразовый клон `/home/deploy/exec-clones/chaskiq-fork-updates-r10m`,
ветка `fork-updates-r10m`. Живое дерево `/home/deploy/github/chaskiq` доступно
для чтения. git pull в клоне не делать; push в origin запрещён, работу заберёт
постановщик через `git fetch` из клона. Рабочая база критериев — коммит
спецификации поверх BASE_SHA, получаемый через `git merge-base HEAD @{u}`.

Сборка и тесты только через Docker под своим UID:GID. Для `bin/ci-local` выставляй
`CI_LOCAL_CACHE=$HOME/.cache/chaskiq-r10m-ci`. Для ручных проверок используй тот
же образ из `bin/ci-local` и `--user "$(id -u):$(id -g)"` на writable mounts.
Кэш подготовлен постановщиком. Внешние API стабить синтетическими данными.

## 3. Задача

| Файл | Методы и нарушения на BASE |
|---|---|
| `telegram/api.rb` | `send_message` — AbcSize 35.3 и MethodLength 31 |
| `twitter/api.rb` | `process_event` и `send_message` — AbcSize 37.8 и 38.24 |
| `twilio_phone/api.rb` | `process_message`, `process_incoming_call`, `process_incoming_event` — AbcSize 42.36, 35.45 и 45.28 |

Исполнитель пишет характеризацию и рефакторинг по варианту программы для
вех с большими методами. Выделяй приватные помощники. Сохрани возвращаемые
значения, условия ранних выходов, исключения, их область обработки, порядок
запросов, ключи и значения строк/хешей, включая различия строковых и
символьных ключей. Поведенческие дефекты вне этой вехи.

## 4. Что проверено

Постановщик запустил RuboCop с конфигурацией без todo в штатном образе
на чистой копии BASE. Получено семь нарушений из таблицы. В todo есть
четыре исключения на эти файлы. Проверено чтением тел методов:

- Telegram проверяет приватность до `as_json`, использует HTML fallback,
  перехватывает ошибки на разборе блоков и передаёт вложения в
  `BlockManager.deliver_attachments` с хуками доставки.
- Twitter обрабатывает каждый DM, пропускает дубликат через `next`,
  различает автора по `for_user_id` и формирует запрос с первым изображением,
  если загрузка вернула данные.
- Twilio Phone сначала маршрутизирует специальное действие, исходящий
  вызов и событие статуса. При новом входящем разговоре создаёт канал и
  блок, затем уведомляет агентов. При статусе сначала пишет событие,
  потом сохраняет SID и передаёт broadcast, затем выполняет обработку статуса.

Подробности сериализации и результата веток нужно подтвердить
характеризацией на BASE. Список примеров в каталоге проб собран из
базового снимка R10l и примеров Slack/WhatsApp, перечисленных в фикстурах.
Координатор сверяет его отдельным полным прогоном BASE.

## 5. План исполнения

1. Добавь три файла `spec/services/message_apis/{telegram,twitter,twilio_phone}_r10m_spec.rb`.
   Используй вызовы исходных публичных входов и стабь внешнюю сеть через
   WebMock. Для сценариев со сложным внешним SDK допустим стаб на границе SDK
   с точными аргументами. Ветки записи проверяй по фактическим записям
   тестовой базы, где это возможно. Пути тестов фиксированы для гейта.
   - Telegram. Приватная заметка, пустой fallback, HTML fallback,
     невалидный сериализованный контент, отсутствие канала, порядок
     сообщений и вложений, точный URI, JSON и заголовки исходящих
     запросов, распределение caption и исход при отказе отправки.
   - Twitter. DM без изображения и с успешной / неуспешной загрузкой,
     первый блок изображения, точное тело DM, приватная заметка. Для
     webhook проверь отсутствие событий, направление к/от агента,
     новый и существующий разговор, дубликат перед новым событием,
     автора, канал, профиль, внешний ID и контент новой части.
   - Twilio Phone. Приоритет маршрутов, вызов агента с существующим
     назначением и без, его доступность и вызов конференции. Входящий
     и исходящий, с ключом разговора и без него, телефон профиля, канал,
     блок, выбор получателей уведомлений и аргументы конференции.
     Для статуса — записанное событие, состав broadcast, сохранение
     SID, ветка завершения и очистки, обработанное и прочее событие.
   - Сверяй payload, результаты и эффекты на BASE до рефакторинга.
     Штатные непредвиденные ошибки BASE зафиксируй в отчёте. Коммит
     `Pin R10m adapter behavior` содержит только три спеки.
2. Отрефактори три `api.rb`. Сохрани область rescue Telegram. В Twitter
   вынеси обработку одного события и сборку вложения. В Twilio Phone
   вынеси ветку подключения агента, подготовку звонка, уведомления и
   завершение конференции. Не меняй контракты вызываемых методов.
   Коммит `Split R10m adapter methods` содержит только три адаптера.
3. Удали четыре строки исключений этих адаптеров из todo, сохранив
   остальные байты файла. Коммит `Drop R10m RuboCop exclusions`.
4. Добавь датированную запись в `CHANGELOG.md` сразу после заголовка.
   Коммит `Note R10m adapter cleanup`. Каждый subject до 50 символов,
   без трейлеров, атрибуции, подписей в тексте или amend.
5. Выполни критерии, ревью и отчёт. В проверках сохраняй вывод. Покажи
   координатору по одной наблюдаемой мутации каждого изменённого метода
   с указанием проверяющего примера. Независимый прогон этих мутаций
   выполняется при приёмке на копии, с восстановлением исходного файла.

директивы RuboCop, пропуски примеров, чтение исходников в спеках и
изменение пробников. Вне коммитов допустимы отчёт и логи в `tmp/`.

  `bash docs/specs/fork-updates-r10m-probes/rspec_gate.sh`
- **AC-002** — точный состав файлов и порядок первых четырёх коммитов, удалены только четыре исключения.
  `bash -c 'B=$(git merge-base HEAD @{u}) && python3 -I docs/specs/fork-updates-r10m-probes/scope_gate.py "$B" final'`
- **AC-003** — финальные версии трёх новых спек зелёные с кодом первого коммита и на финальном дереве.

- **AC-004** — без todo все семь нарушений исчезли, число нарушений по каждой паре файл/коп не выросло.
  `bash -c 'set -o pipefail; B=$(git merge-base HEAD @{u}) && mkdir -p tmp && bash docs/specs/fork-updates-r10m-probes/backlog_gate.sh "$B" | tee tmp/r10m-backlog.log && awk "/^backlog without todo:/ { ok = (\$5 - \$7 == 7) } END { exit !ok }" tmp/r10m-backlog.log'`

  `bash -c 'CI_LOCAL_CACHE=$HOME/.cache/chaskiq-r10m-ci bin/ci-local --only rubocop'`

### Контракт отчёта

В корне клона оставь untracked `report.json` с массивом `criteria`, ровно
7 записей. В каждой записи поля `id`, `command` (дословно из раздела 7),
`status` (`pass`, `fail` или `blocked`), `rc` (число либо null при блоке),
`note` (строка с наблюдаемым итогом или точной ошибкой). Укажи отдельно
модель и итог agy с квитанцией или ошибкой, список мутаций и примеров,
BASE и финальный SHA. При блоке добавь `report-blocked.md`.

## 9. Контракт на невыполнимое

При проблеме среды сохрани команду и точный вывод и выполни независимые
проверки. Если после восстановления среды остаётся блок, доложи о нём и
оставь коммиты в клоне. Если поведение на BASE отличается от предположения,
проверь входные данные, закрепи наблюдаемое поведение и отрази его в отчёте.
Нельзя обходить ошибку изменением критериев или существующих тестов.
